# Finding: prerelease numeric identifiers larger than uint64 are compared lexically, not numerically

- Target / property: Masterminds/semver @ `dd2b995c61c39ddd668b23ac919b04d607be35ab` — property V8 (`TestPBTCompareMatchesSpecModel`): `Compare` must equal an independent SemVer §11 precedence model. Found at 2,000 rapid checks once the generator shared cores between the compared pair (see findings/002); the rapid-shrunk counterexample is `Compare("0.0.0-100000000000000000000.a.0+a", "0.0.0-20000000000000000000") = -1`, model `+1`.
- Minimal counterexample (all parse cleanly with `StrictNewVersion`):
  - `Compare("1.0.0-99999999999999999999", "1.0.0-100000000000000000000")` = **+1**, spec wants **−1** (9.99e19 < 1.00e20).
  - `Compare("1.0.0-100000000000000000000", "1.0.0-20000000000000000000")` = **−1**, spec wants **+1** (1e20 > 2e19).
  - `Compare("1.0.0-99999999999999999999", "1.0.0---")` = **+1**, spec wants **−1**: a numeric identifier precedes *any* alphanumeric identifier (`--` is valid: `[0-9A-Za-z-]+`, not purely numeric), however large the number is.
  - Full reproducer: `reproducers_test.go.txt` (plain Go; exactly these 3 cases fail, 6 ordinary spec-ordering controls pass, and antisymmetry still holds — the order is consistent, just wrong).
- Observed vs expected: `version.go` `comparePrePart` (called by `comparePrerelease` ← `Version.Compare`) detects numeric identifiers with `strconv.ParseUint(_, 10, 64)`. SemVer places no size limit on numeric identifiers, and neither parser imposes one (`validatePrerelease` checks only character set and leading zeros; the only length bound is the 256-byte `MaxVersionLen` on the whole string). Any identifier over `18446744073709551615` therefore fails `ParseUint` and is silently reclassified as *alphanumeric*: two such identifiers fall into the string branch and compare lexically (wrong whenever digit-count and leading digit disagree with numeric order), and against a true alphanumeric identifier the pair is also compared lexically instead of by the numeric < alphanumeric rule. Identifiers that fit in uint64 compare correctly, which is why the boundary cases `max` vs `max+1` accidentally produce the right sign (lexical order coincides there).
- Verdict: **confirmed bug** (not reported upstream; per this run's instructions, local work only). Low severity in practice — prerelease identifiers with 20+ digits are exotic — but it is a clean violation of a documented invariant on fully validated, strict-parser-accepted input.
- Reasoning: not a wrong property — README states Version comparisons "will follow the specification and always include pre-releases … valid with the comparison section of the spec at https://semver.org/#spec-item-11", and §11.4.1/§11.4.2 mandate numeric comparison for numeric identifiers and numeric < alphanumeric precedence, with no magnitude exception. Not documented behaviour either: the library's documented deviations are coercion in `NewVersion`, metadata being ignored, and constraint-mode prerelease gating — none mentions a uint64 ceiling for prerelease identifiers, and the strict parser accepts these versions without error. Reachability: this package is the version/constraint engine under Helm (`Masterminds/semver/v3` is what Helm uses to sort candidate chart versions and to evaluate `Chart.yaml` dependency constraints against registry/index metadata), so `Compare`/`Collection` ordering and constraint checks on prerelease versions flow through `comparePrePart`. The same helper is also reached from `constraintNotEqual`'s patch-dirty branch in constraints.go.
  - Related but **out of scope**: for equal numeric values in different spellings (`"01"` vs `"1"`), `comparePrePart` returns −1 in both directions. That input cannot be produced by either parser or by `SetPrerelease` (leading-zero numerics are rejected); it is only constructible through `New()`, which documents that it does not validate prerelease/metadata. Recorded here, not claimed.
  - Plausible fixes (for a future upstream report): in `comparePrePart`, decide numeric-ness by character class, not by `ParseUint` success, and compare numeric identifiers by (length, lexical) after stripping — or with `math/big` — so overflow is impossible.
