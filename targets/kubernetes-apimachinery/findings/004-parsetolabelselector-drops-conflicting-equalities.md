# Finding: `metav1.ParseToLabelSelector` silently drops conflicting equality requirements on the same key

- Target / property: kubernetes/apimachinery @ `b26d01364f13520dfdecb540fc63253be5b76662` — property M2 (`TestPBTParseToLabelSelectorAgreesWithLabels`): when both parsers accept a selector, `LabelSelectorAsSelector(ParseToLabelSelector(s))` must match the same label sets as `labels.Parse(s)`. Found at 2,000 rapid checks (passed at 100).
- Minimal counterexample: `s = "tier=db,tier=web"`, label set `{tier: web}`.
  - `labels.Parse(s)` keeps both requirements → the selector is a contradiction and matches **nothing**.
  - `ParseToLabelSelector(s)` returns `MatchLabels{tier: web}`, no error; converted back, the selector is just `tier=web` and **matches** `{tier: web}`.
  - The rapid-shrunk original was `"tier=db,tier,tier=web"` on `{tier: web}` (direct: false, converted: true). Reversing the order (`"tier=web,tier=db"`) keeps `tier=db` instead — the survivor is whichever equality comes last.
- Observed vs expected: `ParseToLabelSelector` (`pkg/apis/meta/v1/helpers.go`) routes Equals/DoubleEquals requirements into the `MatchLabels` map with a plain `labelSelector.MatchLabels[req.Key()] = val` assignment, so a second, conflicting equality for the same key silently overwrites the first. The `LabelSelector` representation could preserve the semantics (one value in `MatchLabels`, the other as an `In` match expression, or both as expressions), and the function already returns errors for other unrepresentable inputs ("equals operator must have exactly one value"); it simply never checks for a conflicting duplicate. The result is a converted selector that matches strictly more than the source — the dangerous direction for a weakening conversion.
- Verdict: **confirmed bug** (not reported upstream; the lab reports only on Navid's instruction). Low severity: the input is a degenerate selector (repeated equality key with different values), most likely arising from programmatically merged requirement lists rather than hand-written selectors, but the conversion loses semantics silently and without error.
- Reasoning: not a wrong property — M2 is the function's own documented contract ("This function should be kept in sync with the parser in pkg/labels/selector.go"), and the labels-side semantics for duplicate equalities (conjunction, hence unsatisfiable when values differ) is unambiguous. Duplicates with the *same* value, and equality combined with `in`/`notin`/exists requirements on the same key, all convert faithfully (verified in the probe); only conflicting Equals/DoubleEquals pairs collide, because both target the map.
- Upstream issue: none filed (per lab instruction for this run).
- Fix PR: none. Plausible upstream fixes: error on a conflicting duplicate equality, or route subsequent equalities for an already-mapped key into `MatchExpressions` as `In` requirements. The M2 generator now reuses the first equality value for repeated equality keys (see harness comment) so the suite stays green while this finding stands; reproducer in `reproducers_test.go.txt`.
