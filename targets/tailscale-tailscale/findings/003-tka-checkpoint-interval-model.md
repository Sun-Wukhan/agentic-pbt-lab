# Finding: builder checkpoint appears at the 50th update, not after it

- Target / property: tailscale/tailscale @ 445df50dcf76b6172dc4688c2097c47878f41641, property T6 (`TestPBTTKACheckpointBootstrap`), wave 2 bring-up at checks=100 (failed after 0 tests).
- Minimal counterexample: genesis with one key; apply 50 `AddKey` updates via separate `UpdateBuilder`s, then finalize one more update and expect `[update, checkpoint]`. Observed: the final `Finalize` returned 1 AUM (no checkpoint).
- Observed vs expected: the harness model expected the checkpoint to be generated only once 50 updates were already stored and a 51st was finalized. In fact the checkpoint had already been appended to the 50th update's `Finalize` output (and applied by `Inform`), so the 51st builder correctly found a recent checkpoint and generated none.
- Verdict: wrong property (harness model of `Finalize` was off by one; upstream behaviour matches its code)
- Reasoning: `tka/builder.go` `Finalize` walks back from head looking for a checkpoint, but the loop starts at `i := len(b.out)` — the pending updates count toward `checkpointEvery` (50). With 49 stored updates + 1 pending, the walk reads at most 49 stored AUMs, never reaches the genesis checkpoint, and appends a checkpoint. So a checkpoint is generated by the update that brings the count since the last checkpoint to 50, not by the next one. The harness was fixed to assert exactly this: no checkpoint in updates 1–49, a checkpoint as the tail AUM of update 50, with the full modelled key set in its state. After the fix, T6 passes at checks=100 and checks=2000.
